# Immersive Learning MVP Skill

Use this skill when the user wants to evaluate or shape an AI-driven immersive learning product, especially a web experience that hides learning inside stories, games, simulations, or roleplay.

## Included Reference

- `references/mvp-guidance.md`
  Core feasibility logic, MVP scope rules, recommended first product shape, team needs, timeline ranges, and common traps.

Read the reference before answering. Use it to keep the response grounded in realistic product scope rather than vision-only brainstorming.

## Default Framing

Start from this distinction:

- The full vision is a multi-phase product roadmap.
- The MVP is one narrow, testable experience.

Treat broad ideas such as multi-world learning universes, 3D worlds, video generation, full subject coverage, and open-ended AI characters as roadmap items unless the user explicitly asks for a later-stage plan.

## Default Product Recommendation

If the user is exploring a first version and has not already fixed a different direction, recommend:

- one web-based world
- one target audience
- one core loop
- 3-5 structured sessions or cases
- lightweight assessment

Default example:

- an AI detective world
- 15-25 minute cases
- language, logic, math, and limited English clues embedded in the case flow

## Response Priorities

Structure the answer around these questions:

1. Is the idea feasible
2. What is realistically in scope for MVP
3. What should explicitly wait
4. What team and system components are needed
5. How long MVP will take under different team assumptions

## Non-Negotiable MVP Rules

- Narrow the first release to one world or one scenario family.
- Prefer structured tasks over fully open chat.
- Keep AI outputs constrained by case facts, rules, prompts, and state.
- Separate product excitement from technical feasibility.
- Call out knowledge accuracy risk when the product touches school subjects.
- Avoid presenting 3D, real-time video generation, or all-subject coverage as first-version requirements.

## Timeline Defaults

Use these ranges unless the user provides stronger constraints:

- experienced small team — 6-8 weeks for an internal playable MVP
- experienced solo builder — 10-14 weeks for a basic MVP
- beginner learning while building — 4-6 months for a realistic MVP

When needed, also distinguish:

- demo or prototype
- internal MVP
- stable testable version

## What To Emphasize

- The hardest part is usually product structure, content design, and AI constraint design, not UI alone.
- A strong MVP needs a repeatable task loop, not just an impressive AI conversation.
- Early validation should focus on completion, return usage, and perceived engagement before monetization.

## Do Not Do

- Do not treat a broad vision document as an MVP plan.
- Do not recommend starting with multiple worlds by default.
- Do not assume the first version needs 3D, voice, and video together.
- Do not answer only with encouragement; give a concrete scope cut and timeline.
